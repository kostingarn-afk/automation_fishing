# Design

## Context

Мотивация — `proposal.md`. Текущее состояние, которое определяет форму решения:

- Цикл `loop10.run_cycle` — линейная цепочка с пятью выходами: `OK`, `NO_STRIKE` и три отказа
  через локальный `finish_failure` (`MISS`/`NO_BOBBER`, `LOST`/`NO_BURST`, `LOST`/`TIMEOUT`).
  Исключения `InputBlocked` и `CaptureFailed` в `run_block` превращаются в `WIN_FAIL`.
- `run_block` ведёт блок из 10 циклов и знает номер текущего цикла.
- Трасса — построчная, колонки позиционные, маркер и причина — последние две (`Trace.write`).
  Кода, разбирающего трассу, в проекте нет: только человек и PowerShell-однострочник из README.
- `input.send_key` шлёт `down`+`up` одним пакетом `SendInput` и принимает только символы
  `0x30..0x5A`; пробел (`VK_SPACE = 0x20`) отвергается.
- `probe_input.py` переиспользует `loop10.run_cycle` с именованными аргументами — сигнатура
  должна остаться совместимой при значении по умолчанию.
- Окно верификации `VERIFY_WINDOW = (1.2, 2.5)` с уже закрывает цикл `OK`; камера и ROI жёстко
  связаны: сдвиг камеры меняет содержимое кадра и валидность `baseline` следующего цикла.

## Goals / Non-Goals

**Goals:**

- Один прыжок на блок, слот выбирается случайно из 3–10 до первого цикла блока.
- Прыжок выполняется после завершения цикла `K` при любом маркере, кроме `WIN_FAIL`.
- Паузы 1–1.5 с до и после нажатия, независимые.
- Прыжок виден в трассе отдельной колонкой и в консоли.
- `F12` остаётся работоспособным в паузах, ввод не отправляется без foreground.

**Non-Goals:**

- Не менять детекцию, пороги зрения, таймауты фаз, правило вердикта и окно верификации.
- Не вводить флаги запуска (`--no-jump`, `--jump-cycle`): поведение фиксировано, а живая проверка
  гарантирована (прыжок есть в каждом полном блоке).
- Не добавлять второй прыжок, серии прыжков или другие «неигровые» действия.
- Не делать прыжок частью контракта поимки: он не влияет на маркер цикла.

## Decisions

### D1. Прыжок — после подтверждения исхода цикла, а не внутри окна верификации

Клик и подтверждение поимки разнесены окном 1.2–2.5 с. Прыжок внутри него сдвигает камеру раньше,
чем `wait_bobber_gone` проверит исчезновение поплавка, и ломает верификацию. Поэтому паузы
отсчитываются от момента закрытия цикла.

Следствие: от клика до прыжка проходит 2.2–4.0 с (окно верификации + первая пауза). Принято:
«поимка» подтверждается только окном верификации.

Альтернативы: прыжок сразу после клика (ломает верификацию), прыжок по истечении окна вместо
ожидания (теряет подтверждение исхода).

### D2. Прыжок реализуется в `run_cycle`, все выходы сводятся в одну точку закрытия

`run_cycle` получает параметр `jump: bool = False`; `run_block` передаёт `jump=(cycle == K)`.
Внутри цикла появляется общий `close(marker, reason)`: пауза, прыжок, пауза, запись строки трассы.
`finish_failure` сохраняет кадр отказа и печатает сообщение, после чего вызывает `close`.

Почему не обёртка в `run_block`: прыжок должен попасть в строку своего цикла, а «одна строка на
цикл» запрещает отдельную строку события; обёртка также требует шва для подмены ввода в тестах
`main()`.

Почему не отдельная функция на каждом выходе: пять копий последовательности разъедутся.

Совместимость: `probe_input.py` вызывает `run_cycle` без `jump` — значение по умолчанию сохраняет
поведение probe-скрипта.

### D3. Прыжок при любом маркере, кроме `WIN_FAIL`

Выбор пользователя: слот фиксирован, условие «после поимки» не проверяется. Это упрощает модель —
решение принимается один раз на блок, а не переезжает между циклами, и гарантирует один прыжок на
полный блок.

Альтернативы (отклонены): прыжок только после `OK` (в ~20 % блоков фича не срабатывает);
перенос в следующий `OK`-цикл (дополнительное состояние и неопределённость); перевыбор слота
(может не сработать вовсе).

### D4. Колонка `jump` в трассе между `gone` и маркером

Формат: `#NN | cast 0 | burst <мс> | strike <мс> | gone <мс> | jump <мс> | MARKER | причинa`.
`-`, если прыжка не было. Момент снимается непосредственно перед нажатием, после первой паузы.

Почему так: маркер и причина остаются последними двумя колонками, поэтому PowerShell-однострочник
`Select-String '\| OK \|'` из README продолжает работать; внешних парсеров в проекте нет.

Альтернативы (отклонены): отдельная строка события (нарушает «одна строка на цикл, ровно один
маркер»); только консоль (непроверяемо по артефакту).

### D5. Клавиша прыжка — именованный ключ `space` с удержанием

`send_key` принимает имя `"space"` (`VK_SPACE = 0x20`) наряду с символами. Для прыжка `down` и `up`
разнесены во времени на 60–120 мс (как `CLICK_HOLD` для мыши): клиент на 60 FPS не различает
одномоментные события. Каст продолжает использовать прежний путь без удержания — его тайминги
подобраны и менять их незачем.

Альтернативы (отклонены): `down`+`up` одним пакетом (риск «прыжок не принят»); удержание для всех
клавиш (меняет проверенный путь каста).

### D6. Потеря фокуса перед прыжком — пропуск с предупреждением, не `WIN_FAIL`

`input_layer.jump` проверяет foreground до отправки; при отказе `run_cycle` ловит `InputBlocked`,
печатает предупреждение, пропускает вторую паузу и закрывает цикл с его собственным маркером.
Обоснование: прыжок не входит в контракт поимки, а если фокус не вернулся, следующий каст сам
поднимет `WIN_FAIL`. Проваливать блок из-за вспомогательного действия незачем.

Альтернатива (отклонена): считать отказ ввода аварией блока — теряется блок из-за косметики.

### D7. `F12` опрашивается внутри пауз

Обе паузы выполняются через `sleep_checked`: сон шагами 50–100 мс с проверкой `win.stop_requested()`,
по нажатию — `RunInterrupted`. Иначе стоп «залипает» до 1.5 с. Прерванный цикл строку не пишет —
это уже действующее правило (`F12` во время верификации).

### D8. Порядок действий в закрытии цикла

1. Снять момент отказа (`elapsed_ms`) — **до** пауз, иначе `reason@<мс>` включит до 3 с ожидания.
2. Сохранить кадр отказа — **до** прыжка, иначе кадр снят с движущейся камеры.
3. Первая пауза `random.uniform(1.0, 1.5)`.
4. `jump_ms = elapsed_ms()`, нажатие `space`.
5. Вторая пауза `random.uniform(1.0, 1.5)` (пропускается, если прыжок не отправлен).
6. `trace.write(..., jump=jump_ms)`.

### D9. Константы и выбор слота

`demo/loop10.py`: `JUMP_CYCLES = (3, BLOCK_CYCLES)`, `JUMP_PAUSE_BEFORE = (1.0, 1.5)`,
`JUMP_PAUSE_AFTER = (1.0, 1.5)`, `JUMP_SLEEP_STEP = 0.05`.
`demo/input.py`: `VK_SPACE = 0x20`, `KEY_NAMES = {"space": VK_SPACE}`, `KEY_HOLD = (0.06, 0.12)`.
Слот: `jump_cycle = random.randint(*JUMP_CYCLES)` в начале `run_block`, печатается вместе со стартом
блока. Повторов между блоками не избегаем: распределение независимое.

## Risks / Trade-offs

| Риск | Смягчение |
|---|---|
| Каст в воздухе: прыжок длится ~0.8–1.0 с, нижняя граница второй паузы 1.0 с | смотреть цикл `K+1` живого блока; при `MISS`/`NO_BOBBER` поднять нижнюю границу до 1.1–1.2 с (остаётся в пределах 1–1.5 с из спеки) |
| `baseline` следующего цикла снят с неустоявшейся камеры | вторая пауза — не косметика; при систематике увеличить её нижнюю границу |
| Прыжок после `MISS`/`LOST` сматывает леску, если каст всё-таки лёг | цикл уже закрыт отказом, следующий цикл — новый каст; потерь нет |
| Смена формата трассы (7 -> 8 колонок) | внешних парсеров в проекте нет; README обновляется; старые файлы остаются читаемыми человеком |
| Фейки `run_cycle` в `test_blocks.py` ломаются от нового параметра | фейки получают `jump=False`; добавляется сценарий-шпион на выбор слота |
| Прыжок не проверяется офлайн целиком | офлайн проверяются выбор слота, формат строки и отправка `space`; сам прыжок подтверждается живым блоком |

## Migration Plan

- Данные не мигрируются: старые `trace/run_*.txt` (7 колонок) остаются как есть, новые пишутся
  в 8 колонок; различие видно по числу разделителей.
- Откат — обычный откат коммита: новых зависимостей и схем хранения нет.
- Порядок поставки: `input.py` (ключ и отправка) -> `loop10.py` (слот, закрытие, трасса) ->
  `test_blocks.py` -> README -> живой блок.

## Open Questions

- Фактическая длительность прыжка на клиенте 3.3.5: уточняется живым блоком и влияет только на
  нижнюю границу второй паузы в пределах 1–1.5 с, не на спеку и не на состав задач.
- Даёт ли прыжок после неудачного цикла видимые артефакты (сматывание лески, сдвиг персонажа):
  наблюдается в том же живом блоке; при систематике рассматривается отдельным изменением.
