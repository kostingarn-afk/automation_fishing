# Optimization fishing — бот рыбалки для WoW 3.3.5a

Внешняя автоматизация рыбалки в WoW 3.3.5.12340 (WotLK): снимки экрана + инъекция ввода,
без чтения памяти и инъекций DLL. Демо (критерий 1) закрыто; перспектива — в
`wowfish-actualization-plan.md` §7.

Документы: `README.md` — инструкция для человека (запуск, отладка, переезд на новое место);
`openspec/specs/` — источник истины по требованиям; `wowfish-actualization-plan.md` — контекст
и план. Здесь только проектные уточнения к глобальному `AGENTS.md`: язык, форматы подтверждений
и правила делегирования берутся оттуда и не дублируются.

## Запуск

Импорты в `demo/` локальные, поэтому эти команды запускаются из `demo/`:

```bash
cd demo
python loop10.py --countdown 60                     # блоки по 10 циклов до F12, ~3 мин на блок
python test_blocks.py                               # самопроверка логики (работает из любого каталога)
python probe_capture.py                             # окна, размер клиента, границы ROI, состояние кадра; пишет probe/<дата>/capture_client.png
python probe_preflight.py                           # предусловия: фокус, каст, изменение ROI; отсчёт фиксированный, флагов нет
python probe_input.py --countdown 20                # до двух циклов (ветки SendInput / mouse_event), выход после первого OK; ввод в игру!
python probe_splash.py --repeat 5 --countdown 60    # запись каналов в probe/<дата>/
python probe_splash.py --tune ../probe/<дата1> --tune ../probe/<дата2>   # подбор порога, офлайн; отчёт — в каталог первой записи с поплавком
```

Полные флаги и коды выхода — `README.md` §4–§5. Отсчёт по умолчанию 5 с (`win.START_COUNTDOWN`);
для ручного запуска задавайте `--countdown 30–60`. Для `probe_input` достаточно 15–20 с — цикл короткий.

Предусловия в игре: персонаж у воды с удочкой, **Auto Loot = ON**, **Click-to-move = OFF**,
клавиша каста `1`, окно игры в фокусе, в ROI только вода (без красного берега и доспеха).

## Правила работы с игрой

1. Любая команда, которая шлёт ввод в клиент (`loop10`, `probe_input`, `probe_splash`,
   `probe_preflight`), запускается только после явного подтверждения пользователя в формате
   глобального `AGENTS.md`.
2. Перед запуском сообщить: что будет делать, сколько займёт, что нужен отсчёт
   (`--countdown` есть у `loop10`, `probe_input`, `probe_splash`; у `probe_preflight` отсчёт
   фиксированный 5 с и флагов нет — его запускают, уже находясь в игре) и что мышь/клавиатуру
   до конца прогона трогать нельзя.
3. `F12` — аварийная остановка; ею же пользуется пользователь, чтобы закончить сессию.
4. Всплывшее окно поверх игры отбирает фокус → `WIN_FAIL` и остановка сессии. Если пользователь
   работает в терминале рядом с игрой, предупредить об этом до запуска.
5. `probe/` — рабочий каталог; удаление записей — только с подтверждением пользователя: `--tune`
   воспроизводит отчёт лишь по сохранённым записям (`metadata.json` + `frames/`), после удаления
   нужна повторная запись (README §10). README §10 ссылается на это правило.
6. Автоматизация нарушает EULA игры: риск блокировки аккаунта не снимается ничем. Перед первой
   живой сессией и при запуске нового типа команды (запись каналов, живой прогон; подбор порога —
   офлайн, игру не затрагивает) напоминать пользователю (README §10).

## Проверки перед сдачей

```bash
# все команды блока — из корня проекта
python -m compileall -q demo       # синтаксис всех модулей
python demo/test_blocks.py         # 6 сценариев логики блоков, без клиента
openspec validate --all --strict   # спеки и change
```

Изменения в детекции и таймингах подтверждаются одним живым блоком
(`cd demo && python loop10.py --countdown 60`, после 10-го цикла нажать `F12`) и разбором `trace/`.
Живой блок запускать отдельно от проверок выше и не выполнять команды в терминале во время
прогона — это отбирает фокус.
Блок засчитывается при вердикте «принято» (полный блок из 10 циклов, ≥8 `OK`, без `WIN_FAIL`
и без аварийных завершений); коды выхода: `0` — проваленных блоков нет, `1` — был, `2` — окно,
фокус, аргументы или отмена `F12` на отсчёте (штатно). Автоматических тестов на детекцию нет:
единственный источник данных — клиент.

## Workflow

- Требования и решения живут в OpenSpec: `openspec/changes/<id>/` → при архивации попадают
  в `openspec/specs/`. Задачу change закрывать только по наблюдаемой проверке.
- Архивные change (`openspec/changes/archive/`) — история; найденную в них ошибку исправлять
  новым change, а не правкой архива.
- Репозиторий под git (`origin` — GitHub `kostingarn-afk/automation_fishing`); `trace/`, `fail/`, `probe/`, `.opencode/` в `.gitignore`. Историю документации держит git — отдельные копии перед перезаписью не нужны.
- `README.md` — для человека (как запускать и отлаживать), план — контекст и перспектива,
  `openspec/specs/` — требования. Не дублировать одно в другом.

## Особенности окружения (проверено)

| Что | Как обходится |
|---|---|
| `pip` падает на `CERTIFICATE_VERIFY_FAILED` (MITM-корень Kaspersky) | `pip install --use-feature=truststore -r demo/requirements.txt` (из корня; по разрешению пользователя) |
| Консоль CP866 роняет `print` с кириллицей | `capture.configure_console()` + терминал UTF-8 (Windows Terminal, PowerShell 7) |
| `SetForegroundWindow` из фона не срабатывает | стартовый отсчёт `--countdown`, в игру переключается сам пользователь |
| Мгновенный перевод курсора и `down`+`up` одним пакетом клиент не принимает | плавный перевод 100–300 мс, удержание кнопки 60–200 мс (`demo/input.py`) |
| Мягкий красный фильтр ловит блики воды и уводит захват на воду | захват только строгим пресетом `TRACK_*` (`demo/vision.py`), верификация — мягкая |
| Пороги всплеска зависят от сцены и освещения | переподбор `probe_splash.py --tune` после смены места (README §9.4) |

## Известные ограничения

Вторая подсечка — норма для большинства циклов; `OK` означает «клик зарегистрирован», а не
«рыба поймана»; ROI обязан смотреть в воду. Полный список — `README.md` §10.
